Witness-capable mode is restricted to the binary produced by the reviewed `build:binary` path whose independently run ELF/interpreter/shared-library probe exactly equals the closure. Actual execution is bound by `pi.host-executable-launch-receipt.v1`, not a process's copied digest string. A current host-owner launch broker has exactly three direct launch authorities: it launches the one initial `finalizer` from the owner-pinned standalone file; it launches one `closure_probe` from the request-selected sealed-bundle entry only after the live finalizer's accepted probe request; and it launches at most one `integration_recovery_actor` from the owner-pinned finalizer file only after the authenticated abandoned-chain recovery request. It never directly launches the controller, namespace supervisor, or host. The exhaustive role launch matrix is: `finalizer` and `integration_recovery_actor` have parent `external_launch_broker`, source kind `owner_pinned_file`, and the host-owner release artifact's finalizer-byte domain; `closure_probe` has parent `external_launch_broker`, source kind `sealed_bundle_execveat`, and source role `controller_probe`;  `controller` has parent `finalizer`, source kind `sealed_bundle_execveat`, and source role `controller_executable`; `namespace_supervisor` has parent `controller`, source kind `sealed_bundle_execveat`, and source role `namespace_tool`; `host` has parent `namespace_supervisor`, source kind `sealed_staged_root_execveat`, and source role `host_executable`. No other role, parent, source kind, or digest-domain relation exists. For each sealed-bundle child, its parent creates the kernel gate, copies exactly the selected source-bundle entry into a dedicated anonymous memfd named `pi-<role>-<launch_id>`, rehashes it, applies exactly `F_SEAL_WRITE|F_SEAL_GROW|F_SEAL_SHRINK|F_SEAL_SEAL`, and uses `execveat(fd,"",...,AT_EMPTY_PATH)`; the composite source-bundle file is never executed. The host instead opens sealed staged `/host/pi` no-follow as `O_RDONLY|O_CLOEXEC` through the retained staging-root descriptor, verifies `FD_CLOEXEC`, and executes that exact inode with `execveat(fd,"",...,AT_EMPTY_PATH)`. Every launch parent creates exactly one `socketpair(AF_UNIX,SOCK_SEQPACKET|SOCK_CLOEXEC)` pre-entry gate, retains only its parent endpoint, installs only the child endpoint as fixed FD10 with `FD_CLOEXEC` cleared and verified before `execveat`, and closes every duplicate/opposite endpoint. Each executable begins with a reviewed static pre-entry trampoline that performs no ambient read or role operation, sends exactly the one-byte `0x00` trampoline-ready frame on FD10 with no ancillary item, then blocks in `recvmsg` for exactly the one-byte `0x01` release frame with no ancillary item. EOF, timeout, truncation, any other byte/length, or ancillary data exits without role entry. After the valid release, the trampoline closes FD10 and transfers control exactly once; it never raises `SIGSTOP`, and no `SIGCONT` participates in the protocol. The retaining parent must receive the ready frame before constructing a launch candidate or requesting broker attestation, and may send the release only after the required persisted launch receipt and role registration exist. `pi.host-launch-broker-channel-binding.v1` is exactly `{schema,broker_service_identity,broker_process_identity,broker_child_subreaper,finalizer_launch_id,finalizer_pid,finalizer_starttime,requester_fd,requester_endpoint_device,requester_endpoint_inode,broker_endpoint_device,broker_endpoint_inode,transport,credential_policy,max_frame_bytes,launch_broker_channel_binding_digest}`. Broker process identity is exactly `{pid,starttime,proc_directory_inode}` and `broker_child_subreaper=true`; before any launch the broker calls `prctl(PR_SET_CHILD_SUBREAPER,1)`, requires `PR_GET_CHILD_SUBREAPER=1`, and remains alive until it has reaped every direct or adopted process in the launch lineage. Broker identity is exactly `{kind:"pi_host_launch_broker",owner_role:"pi-host-owner",repository_id:"pi-mono",component_id:"pi-coding-agent-launch-broker"}`, requester FD is `7`, transport is `unix_seqpacket`, policy is `kernel_credentials_plus_closed_frames`, and maximum is `1048576`. The broker creates one `SOCK_SEQPACKET|SOCK_CLOEXEC` pair before every ordinary finalizer launch, retains its endpoint, installs only the requester endpoint as finalizer FD7 with `FD_CLOEXEC` cleared and verified before exec, enables `SO_PASSCRED` on both receivers, receives the FD10 trampoline-ready frame, verifies the FD7 tuple while the finalizer remains blocked on FD10, and binds that tuple into the finalizer launch receipt. Integration and production both retain this unique FD7 through finalizer exit; production alone additionally installs replay FD8. `SO_PASSCRED` is a receive-endpoint property. Protocol senders never supply an explicit `SCM_CREDENTIALS`; Linux supplies exactly one kernel-generated `SOL_SOCKET/SCM_CREDENTIALS` item on every received FD7 frame. A receiver validates all three `ucred` values: `pid` equals the direction-selected sender below, `uid`/`gid` equal that process's live real IDs visible to the receiver, and a no-follow `/proc/<pid>` read joins the PID to the required starttime and proc-directory inode. Broker and finalizer must share the same PID and user namespaces. Ancillary data is an unordered cmsg multiset: a descriptor-free frame has exactly one credentials item and no rights/other item; a descriptor-bearing frame has exactly one credentials item plus one `SCM_RIGHTS` item whose descriptor order is normative. Receivers use `MSG_CMSG_CLOEXEC` and reject truncation, duplicate credentials, multiple rights items, unknown ancillary types, descriptor drift, or process-identity drift. FD7 finalizer-to-broker frames require the finalizer launch-receipt PID/starttime: closure-probe request carries one sealed source-bundle FD; each launch-attestation request carries exactly ordered `pidfd,executable_fd`; production pidfd handoff carries exactly ordered controller, namespace-supervisor, and host pidfds; and the signed host-lineage closeout carries no descriptor. FD7 broker-to-finalizer frames require `broker_process_identity` and no descriptors: the five ordered closure-probe response bodies, each launch response/receipt/read-receipt body, the byte-identical relayed production pidfd-handoff acknowledgement, and the current host-owner store read-receipt body naming the persisted host-lineage closeout. No other successful FD7 frame or credential/descriptor combination is legal.

Each append uses `BEGIN IMMEDIATE`, validates exact lock-local prior head/revision against that anchor plus every preceding acknowledgement, inserts artifact/record/new head in one transaction, `COMMIT`, then fsyncs DB and parent directory before acknowledgement. SQLite rollback journal recovery runs on open; integrity check, application/user version, schema SQL bytes, and full record/head/digest chain are verified before use. Uncommitted/orphan rows are absent after recovery; committed head without complete BLOB/record rejects permanently. Controller holds writer lock through second-attempt suppression, closes it before FD6 terminal prepare, and finalizer may acquire only after the credential-authenticated prepare names the exact durable prior head; this compare-and-swap is the sole writer handoff. Finalizer persists the transcript and atomically marks the store instance terminal-sealed in the same transaction; terminal seal forbids every later append. Terminal authority resolution binds the sealed head and acquisition pin but has null final read-receipt digest. Finalizer releases the lock after terminal ledger persistence and controller-exit observation (or, on any unterminalizable-survivor branch, closes the DB/descriptors and exits before transferring recovery ownership), then obtains one current host-owner store receipt for the immutable sealed head. The resolver requires the store control resolution, acquisition pin, and current read receipt and joins every acknowledgement to the complete record/head chain; a copied/restored/alternate file cannot satisfy that external current-head anchor. The proof is constructed after ledger and store receipts and is not appended to this store. Because the per-attempt instance is terminal-sealed and cannot advance, its final receipt remains current; deterministic proof reissuance uses the same receipt bytes.

## Normative JSON profile

Input is bounded strict UTF-8 JSON with no BOM/trailing data and duplicate-key rejection before object construction. Legal number tokens are only `0|[1-9][0-9]*`, range `0..9007199254740991`; booleans are never integers. Reject negative/decimal/exponent/NaN/Infinity, lone surrogates, Unicode noncharacters, and non-NFC strings. Depth is at most 64.

Canonical bytes are RFC 8785 JCS under that integer-only I-JSON profile. Object keys sort by UTF-16 code units; arrays retain normative order. Equality is type-exact.

JSON object digests are:

```text
sha256(ASCII(domain) || 0x00 || JCS(object without exactly its top-level self-digest field))
```

Raw byte digests are:

```text
sha256(ASCII(domain) || 0x00 || exact_bytes)
```

Every digest is `sha256:` plus 64 lowercase hex characters.

## Execution and attempt identity

`execution_instance_digest` preimage is exactly:

```text
{host_runtime_manifest_digest, boot_nonce, extension_api_version}
```

Every nonce is an independent 32-byte Linux `getrandom(...,0)` draw, encoded as 64 lowercase hexadecimal characters; only `EINTR`/partial completion retries are legal. Attestation-owner evidence rejects reuse of `(host_runtime_manifest_digest,boot_nonce)`.

`prompt_run_attempt_digest` preimage is exactly:

```text
{execution_instance_digest, execution_generation, attempt_ordinal,

```
