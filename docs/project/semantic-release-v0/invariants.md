# Semantic Release Protocol v0 — Normative Invariants

[`protocol.schema.json`](protocol.schema.json) owns closed shape; this file owns cross-object and operational behavior; the Decision-53 RFC owns governance boundaries. All three must agree. Missing facts, unavailable references, unknown values, conflicts, or disagreement fail closed. Fixtures prove examples only and grant no authority.

## 1. Canonical input and digest rules

1. Input is raw-token-validated, duplicate-key-free UTF-8 JSON without BOM or trailing data. Object-key duplication is rejected at every depth before object construction. The only legal number token is `0|[1-9][0-9]*`; leading zero, minus (including `-0`), decimal, exponent, NaN, and Infinity forms are rejected before conversion. Also reject malformed UTF-8, lone surrogates, Unicode noncharacters, non-NFC strings, booleans used as integers, and integers outside `0..9007199254740991`.
2. JCS is RFC 8785 after those I-JSON restrictions. Object keys sort by UTF-16 code units. Arrays retain normative order. Strings and `minLength`/`maxLength` count Unicode code points and must also fit the same UTF-8 byte ceiling.
3. Protocol digests are `"sha256:" + lowercase_hex(SHA-256(UTF8(domain) || 0x00 || preimage))`. JSON preimages are JCS after removing exactly the top-level self-digest field. The coordinate digest uses the complete coordinate. Raw blob and semantic payload preimages are unmodified bytes.
4. The domain is `semantic-release.<name>.v0`, where `<name>` is the hyphenated object name in `validate_fixtures.py` and `validate_fixtures.mjs`. Raw bytes use `semantic-release.raw-blob.v0`; semantic payload bytes use `semantic-release.semantic-payload.v0`; coordinates use `semantic-release.coordinate.v0`.
5. Every nested digest remains in the preimage. A missing or unequal embedded digest returns `digest_mismatch` after decode/schema checks and before authority checks. No other failure may mask a digest mismatch at that precedence.
6. Aggregate limits remain 16 MiB per JSON artifact, 100,000 manifest entries, 256 MiB described bytes, nesting depth 64, and caller deadline at most 300 seconds unless a closed owner policy is stricter. Validation is offline and performs no fetch.
7. Every set-valued array is duplicate-free and UTF-8 sorted. Manifest entries sort by `(path UTF-8, kind)`; votes by `(owner_id UTF-8, owner_key_id UTF-8)`; change rows by `(semantic_id UTF-8, category UTF-8)`.

## 2. Trees, capsule archive, and exact projection

1. Logical paths are relative NFC POSIX paths with no empty, `.`, `..`, backslash, NUL, drive, traversal, case-fold collision, or normalization collision. Every non-root parent directory is listed.
2. Source manifests admit regular files, directories, and bounded relative symlinks. They reject submodules, special files, hard-link ambiguity, uncommitted content, ignored additions, and source-revision drift. `clean_committed=true` is independently verified.
3. Material manifests admit only directories and regular files with significant modes `0644`, `0755`, and directory `0755`. Complete-tree verification rejects every missing, extra, duplicate, linked, sparse-ambiguous, or metadata-dependent entry.
4. `semantic-capsule-archive-linkage.v0` binds the complete archive manifest, compiled payload manifest, exact payload root, capsule metadata path, and archive format. Archive metadata is not allowed to alter payload identity.
5. `semantic-payload-projection.v0` is the complete allow-list from capsule paths to consumer paths. Each row binds path, mode, byte length, and content digest; directory rows use null length/digest. Source paths are UTF-8 sorted and unique; destination paths are independently unique. Their sets must equal, respectively, every payload entry under `payload_root` and every consumer entry. The archive entry set equals exactly the metadata path, payload root directory, and prefixed payload entry set; no extra archive entry is legal. `projection_mode=exact_no_extra_no_missing` is a total bijection, not merely equal row counts.
6. Capsule/archive identity is acyclic: capsule → archive linkage → archive manifest and closed metadata. The metadata contains only namespace, version, payload manifest, and fixed `no_capsule_archive_or_linkage_digest` mode; its exact JCS raw-byte digest and length equal the metadata archive entry. It cannot contain capsule, archive, or linkage digests. A materialization receipt must equal all capsule/projection/archive/manifests and the actual tree. Any duplicate, omitted, extra, remapped, changed, cyclic, or drifting entry returns `projection_mismatch` before mutation.
7. Source, payload, capsule archive, staged consumer tree, and active consumer tree are distinct roots. ROCS tool identity is bound by build/materialization receipts, not capsule identity.

## 3. Closed semantic-owner authority and trust

1. The semantic owner maintains immutable `semantic-owner-set.v0`, `semantic-approval-predicate.v0`, `semantic-compatibility-policy.v0`, `semantic-owner-policy.v0`, `semantic-trust-root.v0`, rotation, revocation, approval, and publication records on the owner surface.
2. The owner policy binds exact governing scope, owner set, approval predicate, compatibility policy, owner-controlled out-of-band trust bootstrap mode, prior policy, mandatory old-root rotation, and fail-closed revocation behavior. A consumer, ROCS, Pi, or AK cannot replace or mint these objects.
3. Owner-set members and key IDs are closed and unique. A vote is eligible only when its owner is active, its key is in that member's pinned key set, and its candidate digest equals the approval candidate. One owner counts once even if multiple keys vote.
4. `threshold` requires at least its exact integer of distinct eligible active owners and that integer must be in `1..active-owner-count`. `unanimous` requires exactly every active member and requires `threshold == active-owner-count`; a merely sufficient but unequal threshold is invalid. Revoked owners/keys return `trust_revoked`; absent, duplicate, or insufficient eligible owners return `approval_threshold_unsatisfied`.
5. Owner approval binds an exactly equal namespace, policy, set, and predicate chain, a closed typed action, its independently recomputed `semantic-release.approval-action.v0` digest, unique votes over that same action digest, and a canonical accepted AK decision reference. Typed actions are `release`, `trust_rotation`, `trust_revocation`, or `compatibility_override`; action-specific fields are closed. The predicate is recomputed; the approval's existence is not itself proof that it passed.
6. The local trust chain is external owner-controlled root pin → owner policy/set/predicate → approval → publication → coordinate → capsule → manifests/blobs. A capsule, consumer copy, build receipt, AK record, or Pi receipt cannot bootstrap the root.
7. Rotation exactly binds current old-root ID/revision/digest, a closed new root whose prior digest is old root, equal namespace/policy/set/predicate across both roots, policy, rotation, and approval, new revision `old+1`, equal rotation revision, and a typed rotation approval repeating every transition and authority field. Policy, approval, root, or revision drift is `trust_reference_stale`; a revoked old root is `trust_revoked`.
8. Revocations are append-only records with revision `prior+1`, target kind/digest (including root), effective ledger revision, reason, typed approval repeating those fields, and exact prior revocation head. Locally known revocation wins over cached trust. Missing, stale, skipped, mismatched-policy, or mismatched-approval state fails closed.
9. Offline cached trust is usable only if root revision, ledger revision, and local revocation head meet the external pins. v0 does not claim protection when both the owner-controlled root store and verifier are compromised.

## 4. Executable compatibility, SemVer, and lifecycle

1. `semantic-compatibility-policy.v0` contains exactly one UTF-8-sorted rule for each of the ten closed categories. Each rule fixes classification, SemVer effect, optional typed condition kind, and override permission. Policy severity is `patch < minor < major < unknown`; zero-major exceptions are absent unless explicitly enabled (v0 fixtures disable them).
2. Conditions are data, not prose. The operators are `evidence_digest_equals` (both digest operands non-null/equal), `consumer_protocol_at_least` (both integer operands non-null and actual ≥ expected), and `deprecation_interval_at_least` (same integer relation). `satisfied` equals recomputation. Condition IDs and references form a cardinality-preserving exact bijection: every policy-required condition is present once, each condition ID is referenced by exactly one change, and every report condition is referenced once; shared references, duplicate, missing, surplus/unreferenced, false, or ill-typed conditions return `compatibility_rejected`.
3. Every change is classified once under the bound policy. Overall classification/effect is the maximum. `unknown` returns `compatibility_unknown`. `identifier_reuse` is always breaking/major and never overrideable.
4. For prior `A.B.C`, patch requires the same major/minor and a greater patch; minor requires a greater minor in the same major or a greater major; major requires a greater major. Regression, equality, prerelease weakening, or an insufficient bump returns `semver_violation`.
5. An override is a separately digested owner object bound to namespace, policy, the exact embedded change and independently recomputed change digest, source classification/effect, target classification/effect floor, executable true condition, and typed owner approval repeating the complete override (namespace, policy, embedded change and digest, source and target classification/effect, and full condition). The approved SemVer floor is never below the source floor; `unknown` fails closed at `major`. Report override digests exactly equal used overrides: omission, surplus, duplicate, or drift rejects. It may resolve only policy-allowed cases; it cannot legalize identifier reuse, erase conditions, lower a SemVer floor, or bypass lifecycle.
6. Deprecation binds namespace/semantic ID/coordinate/revision and exact prior lifecycle head. Removal repeats namespace/ID, binds that deprecation digest/revision as its prior lifecycle head, uses a strictly later accepted-ledger revision, binds the exact compatibility policy and equal policy interval, and binds the prior tombstone registry. Every namespace/ID/revision/interval mismatch is `lifecycle_violation`.
7. The resulting tombstone registry has revision `prior+1`, points to the exact prior registry, is byte-for-byte the prior entry set plus exactly the removed/renamed ID with exact reason and removal/rename origin, and has no extras. Lifecycle namespace, coordinates, ledger revisions, policy interval, deprecation head, current lifecycle head, and prior registry all bind exactly. Removed/renamed IDs remain permanent across withdrawal/revocation and cannot return under any category or override.

## 5. Publication transaction and status machine

1. One namespace has one append-only ledger. `(namespace, semantic_version)` binds permanently to one capsule digest. Same coordinate plus same replay key is idempotent and returns the existing record; a different capsule at that version is `version_conflict` forever.
2. `semantic-publication-transaction.v0` binds operation, coordinate, owner approval, expected prior revision/head, replay key, and status reason. `publish` has null reason; `withdraw`/`revoke` require a reason.
3. Before mutation, the publisher checks lock ownership, exact namespace, version uniqueness, current revision/head, predecessor, trust, approval, policy, source, capsule, projection/archive, and compatibility. Wrong revision is `publication_conflict`; same revision with another expected head is `publication_fork`. Neither mutates state.
4. The journal states are `prepared/not-linearized/discard`, `committing/linearized/complete`, `committed/linearized/none`, and `aborted/not-linearized/discard`; every other tuple is `recovery_needed`. Its resulting record, revision, and head are present in every state so recovery can validate intended effects.
5. Identity is acyclic: transaction → resulting publication/status record → journal → marker. The resulting record binds the transaction and prior head but never journal/marker; journal binds transaction and the resulting record digest as both resulting record and ledger head; marker binds transaction, journal, the same resulting record/head/revision, and completed fsync. No raw future stub or backward digest is legal.
6. Publication stages blobs/result, fsyncs, then CASes one same-filesystem durable head as sole linearization. Recovery validates state effects, not only enum tuples: before linearization it removes staging while revision/head remain byte-equal and no marker exists; after linearization it removes staging and ensures exact resulting revision/head plus marker. Re-run is idempotent; a loser never overwrites a winner; unsupported primitives perform no mutation.
7. Publish result repeats transaction coordinate/namespace/approval, uses revision `expected+1`, and binds expected prior head. Status results admit only `published → withdrawn`, `published → revoked`, `withdrawn → revoked`; each resolves and validates the complete prior status object, repeats operation-matching transaction coordinate/approval/reason, prior status digest, and next revision. The journal prior pointer equals the canonical prior journal head. Their journal/marker bind the transition digest as resulting head. Recovery resolves the exact status record and full commit-marker object: marker transaction, journal, record, revision, and head must all equal the recovered journal; booleans asserting marker presence are insufficient. Revoked is terminal; history never rewrites bytes or frees versions.

## 6. Canonical AK decision membrane and consumer chain

1. Issuer-kind checks run for every structurally valid subject before its domain rule, including expected-rejection subjects; a subject cannot hide issuer substitution behind another error. Every protocol decision uses `semantic-ak-decision-reference.v0`, never an arbitrary digest-only assertion. It binds stable AK repository/runtime, decision ID/revision/record digest, accepted ADR, scope, revocation/supersession, exact activation/evidence/rollback/stop, and a canonical AK store locator with store ID/revision/head and revocation head.
2. A usable reference is accepted, accepted-ADR, unrevoked, unsuperseded, accessible, and exact for scope. The supplied store locator must equal the independently read canonical store locator, store head, and revocation head, and the decision-record digest must equal the current record selected by that head. Copied/stale locators, stale revocation heads, or superseded records fail closed. AK links lineage; it never becomes owner authority.
3. Consumer intent binds stable consumer repository identity/revision, coordinate, runtime, posture, compatibility acceptance, discriminated rollback target, canonical decision, trust reference, verifier contract, and limits. Rename increments identity revision; a fork gets a new repository ID.
4. Owner acceptance is separately issued by the repository's consumer owner. It binds exact intent, owner, governing scope, posture, canonical decision, intent validity, monotonic activation-epoch ceiling, and revocation. ROCS/Pi/AK cannot self-certify acceptance.
5. Materialization requires that chain plus exact capsule/archive/projection, complete trees, compatibility, runtime, rollback readiness, transaction/journal/marker, and prior receipt. It atomically replaces only the materialized-generation pointer. Its issuer is ROCS and its claim is technical verification only.
6. Activation is a separate consumer-owner receipt. It binds acceptance/materialization, target coordinate/runtime, scope, epoch, canonical gate decision, and the decision's exact activation target/evidence/rollback/stop digests. Every expansion gate requires a new accepted decision and activation receipt.
7. Candidate fan-out uses two distinct `semantic-non-authorizing-task-contract.v0` objects: `decision-53-ak-coordination` in `softwareco/owned/agent-kernel` has no allowed worktree paths and coordination-only evidence/rollback ownership; `decision-53-first-consumer-canary` in `softwareco/pi-canary-consumer` has exactly the three RFC-listed paths, consumer-owner rollback, and required consent/materialization/gate/rollback evidence. Both remain `candidate_not_created` with every authorization boolean false. Shared task identity/owner, changed repository/path sets, or any authorization claim is `self_certification`.

## 7. Generation, Pi delivery, and AK linkage

1. ROCS generation is legal only from the current activation store head whose digest and revision equal both generation head fields and the supplied activation receipt's recomputed self-digest/revision. A substituted activation object is invalid even when generation repeats the current pointer. That receipt is `activated`, unrevoked, and unsuperseded, and generation coordinate/runtime equal activation coordinate/runtime byte-for-byte. Historical, deactivated, revoked, superseded, non-head, coordinate-drift, runtime-drift, or head-revision-drift input returns `activation_not_current` before generation.
2. ROCS generation issuer/claim is `rocs/generated_output_only`. Candidate IDs and pack digests are sorted/unique. `matched` proves deterministic generation only.
3. Pi delivery is a closed discriminated union:
   - `delivered` uses `delivered_to_prompt_run_only` and requires prompt-run and delivered-execution digests;
   - `suppressed` uses `delivery_suppressed_only`, requires a closed suppression reason, and forbids prompt/delivered fields;
   - `failed` uses `delivery_failed_only`, requires an error digest, and forbids prompt/delivered fields.
4. Pi issuer is `pi`. Only `delivered` proves binding to a prompt run; none proves reading, interpretation, influence, or correctness.
5. AK evidence linkage binds canonical task, decision, evidence, activation, and ROCS generation. Pi receipt is optional specifically for generation-only lineage; when delivery is claimed it must bind the exact Pi receipt. Empirical outcome remains optional and separately owned.

## 8. Axis-discriminated rollback and immutable typed history

1. Targets are closed: `semantic` switches an available coordinate and retains runtime; `runtime` retains semantics, switches available runtime, and binds mandatory revalidation; `no_prior_disable` disables semantics, retains runtime, and binds disable/rehearsal; `combined` embeds exact semantic/runtime targets and order.
2. A request issuer is the consumer owner. Its activation digest and object select the canonical current activation pointer/revision; `from_state` is enabled and coordinate/runtime equal that activation; its owner decision is current under canonical AK head; its recovery runtime differs from active runtime and remains independently usable. A closed `semantic-rollback-availability-proof.v0` resolves the concrete target materialization, target coordinate/runtime, runtime revalidation, disable/rehearsal facts, canonical activation, and recovery runtime. Missing/drifting target, activation, decision, revalidation, recovery, or disable proof is `rollback_unavailable` before mutation.
3. Receipt request digest, target kind, and before-state exactly equal the request. Stage names are complete, unique, and exactly target order (`semantic`, `runtime`, `disable`, or both combined stages). `completed`/`not_started` has null stage error; `failed` has non-null stage error. Stage outcomes are monotone: completed stages form a prefix, at most one failed stage follows, and every later stage is `not_started`. Receipt `failure_stage` and overall error equal that failed stage exactly. The after-state is recomputed by applying completed stages in order.
4. Semantic completion changes only coordinate. Runtime completion changes only runtime and receipt revalidation equals target proof. Disable completion yields `enabled=false`, null coordinate, and byte-equal retained runtime. Result is `rolled_back` for semantic/runtime/combined success and `disabled` only for no-prior completion; full success has all stages completed and null overall error.
5. Combined partial failure has at least one completed and one failed stage, errors, recomputed partial state, a new `rollback` history head, result `partial_failure`, and null supersession. It never claims full success or supersedes activation.
6. `failed` has at least one failed and no completed stage, non-null error, byte-equal state, exactly unchanged typed history head, and null supersession. Success has a distinct `rollback`/`disable` head and supersedes exactly the active activation. Every changed head resolves to `semantic-rollback-history-transition.v0`, whose prior canonical head, request, result, states, stages, failure cause, and supersession equal the receipt; `history_head_before` equals the canonical current activation/history pointer. Any other completion/error/history/supersession combination is `history_conflict`.
7. Optional AK/Pi rollback cross-links are both null or both present. When present they equal the exact AK linkage/Pi receipt, and AK activation equals request activation; partial/failed receipts may omit them. Rollback uses lock/journal/fsync/atomic-pointer discipline, appends history outside replaceable roots, and never edits publication, activation, prior receipts, or audit.

## 9. Audit, retention, and failure precedence

1. Timestamps occur only in `semantic-audit-envelope.v0`. `recorded_at` matches `YYYY-MM-DDTHH:MM:SSZ`, uses UTC exactly, has Gregorian year `0001..9999`, and is a real date/time. Both validators parse components and round-trip outside annotation-only schema format; year zero and `2026-02-30T12:00:00Z` are invalid.
2. Audit envelopes bind artifact schema/digest, event, issuer, sequence, prior envelope, and self-digest. Re-observation appends another envelope.
3. Retention is namespace/consumer lifetime plus at least seven years. GC traces every ledger/status/revocation head, coordinate, capsule/archive/projection, active/rollback target, receipt, audit envelope, legal hold, and typed history head. Version bindings and tombstones are permanent.
4. Deterministic precedence is decode/I-JSON → schema → `digest_mismatch` → authority/trust → compatibility/lifecycle → staging/projection/tree → pointer mutation → rollback availability/mutation. Details sort by key.
5. Required errors include all closed codes in the schema. In particular stale CAS is `publication_conflict`, divergent head is `publication_fork`, version reuse is `version_conflict`, invalid executable conditions are `compatibility_rejected`, invalid dates are `malformed_input`, and stale activation is `activation_not_current`.
