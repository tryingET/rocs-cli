# Semantic Release Protocol v0 — Normative Invariants

[`protocol.schema.json`](protocol.schema.json) owns closed shape; this file owns cross-object and operational behavior; the Decision-53 RFC owns governance boundaries. All three must agree. Missing facts, unavailable references, unknown values, conflicts, or disagreement fail closed. Fixtures prove examples only and grant no authority.

## 1. Canonical input and digest rules

1. Input is raw-token-validated, duplicate-key-free UTF-8 JSON without BOM or trailing data. Object-key duplication is rejected at every depth before object construction. The only legal number token is `0|[1-9][0-9]*`; leading zero, minus (including `-0`), decimal, exponent, NaN, and Infinity forms are rejected before conversion. Also reject malformed UTF-8, lone surrogates, Unicode noncharacters, non-NFC strings, booleans used as integers, and integers outside `0..9007199254740991`.
2. JCS is RFC 8785 after those I-JSON restrictions. Object keys sort by UTF-16 code units. Arrays retain normative order. Strings and `minLength`/`maxLength` count Unicode code points and must also fit the same UTF-8 byte ceiling.
3. Protocol digests are `"sha256:" + lowercase_hex(SHA-256(UTF8(domain) || 0x00 || preimage))`. JSON preimages are JCS after removing exactly the top-level self-digest field. The coordinate digest uses the complete coordinate. Raw blob and semantic payload preimages are unmodified bytes.
4. The domain is `semantic-release.<name>.v0`, where `<name>` is the hyphenated object name in `validate_fixtures.py` and `validate_fixtures.mjs`. Raw bytes use `semantic-release.raw-blob.v0`; semantic payload bytes use `semantic-release.semantic-payload.v0`; coordinates use `semantic-release.coordinate.v0`.
5. Every nested digest remains in the preimage. A missing or unequal embedded digest returns `digest_mismatch` after decode/schema checks and before authority checks. No other failure may mask a digest mismatch at that precedence.
6. Every JSON file is at most 16 MiB; each differential shard is strictly under 16 MiB and the deterministic generator targets at most 12 MiB. Python and Node load every schema, golden file, differential manifest, and shard with the same race-safe sequence: open with OS no-follow semantics; `fstat` an ordinary regular file no larger than 16 MiB; read no more than `limit+1` bytes; compare the open descriptor's device/inode/mode/size/mtime/ctime before and after and compare the still-non-symlink path identity/size; reject symlink, replacement, growth, truncation, mutation, or oversize; compute raw SHA-256; for shards compare manifest byte length and raw hash; only then decode strict UTF-8 without BOM and parse at nesting depth at most 64. Validation is offline, admits only manifest-listed root-local shard basenames, performs no fetch, and rejects traversal, network-like paths, missing shards, and extra generated shards. Other aggregate limits remain 100,000 manifest entries, 256 MiB described bytes, and caller deadline at most 300 seconds unless a closed owner policy is stricter.
7. JSON equality is type-exact: booleans never equal integers in `const`, `enum`, or relational checks. Every set-valued array is duplicate-free and UTF-8 sorted. Manifest entries sort by `(path UTF-8, kind)`; trust-root key IDs are UTF-8 sorted and unique; votes by `(owner_id UTF-8, owner_key_id UTF-8)`; change rows by `(semantic_id UTF-8, category UTF-8)`.
8. Before any relational rule, the subject, acquisition config and pins, verifier input, authority manifest, snapshot and owner receipts, proof bundle, and every resolved proof object pass explicit expected-type/reference validation: I-JSON, closed schema, expected protocol type, self-digest, normative ordering, and owner/issuer scope where applicable. Nested pin, receipt, binding, repository, proof, and parameter shapes use explicit `$defs` validation. Invalid shape/order is `malformed_input`, invalid issuer is `issuer_scope_violation`, and stale self-digest is `digest_mismatch`; no relational failure may mask them.

## 2. Capability-Pinned Owner-Receipt Authority Proof Graph

1. Every invocation has an exact subject and closed `semantic-authority-acquisition-config.v0`, `semantic-authority-verifier-input.v0`, `semantic-authority-snapshot.v0`, and `semantic-authority-proof-bundle.v0`. The verifier also binds the digest of the normative `semantic-authority-rule-role-manifest.v0`. Rule, subject schema/digest, manifest/config/snapshot/bundle digests, action floor, collator, and collation scope agree exactly. The snapshot and configuration are exogenous verifier inputs and MUST NOT occur as proof-bundle nodes. Their self-digests establish deterministic identity, not owner truth.
2. The acquisition config contains an exact UTF-8-sorted set of `semantic-owner-acquisition-capability-pin.v0` objects and has `live_acquisition_implemented=false`. Every pin binds role, category, owner surface/ID, complete stable repository identity, acquisition contract and contract/distribution digests, store ID/head/revision, typed fact value/digest, freshness CAS token, and required action-epoch floor. Every receipt-source manifest mapping independently hard-pins the complete acquisition contract, contract digest, distribution digest, and capability digest. Config, pin, receipt, and binding may not coherently rewrite that normative tuple. Each receipt repeats the exact pin self-digest. This explicit local pin terminates proof recursion; the packet does not claim that any live capability has been provisioned or exercised.
3. The snapshot contains only UTF-8-sorted, unique `semantic-owner-store-read-receipt.v0` objects. A receipt repeats exactly one configured pin and is issued by that pinned owner under `owner_store_read_only`. It repeats repository, acquisition contract/distribution, store ID/head/revision, typed fact value/digest, freshness token, action epoch, and floor. The collator has `transport_only_no_receipt_issuance`, differs from every receipt issuer, and cannot mint, rewrite, recategorize, or combine owner facts into a new fact. Receipt action epoch equals snapshot action epoch and is at least both receipt and config floors. Fact digest and `semantic-release.owner-store-freshness-cas.v0` token are independently recomputed. Any category/owner/repository/pin/contract/distribution/head/revision/fact/freshness substitution is `issuer_scope_violation`.
4. Role→category→owner→repository→capability mapping is closed. Semantic trust, revocation, publication, lifecycle, and per-owner vote proofs are semantic-owner facts; AK store/decision/task state is AK-owned; acceptance, activation, and history are consumer-owner facts; recovery identity/runtime/epoch is recovery-controller-owned. Publication recovery before-state is a typed semantic-owner receipt; after-state and the non-durable intent descriptor are recovery-controller-issued; a durable publication commit marker remains semantic-owner-owned. Every approval vote has exactly one `owner_vote_proof` receipt whose owner ID/key/action/proof equal the vote and whose capability pin is voter-specific. Opaque vote digests and collator-issued votes reject.
5. The proof bundle is complete and digest-indexed. Every node key equals the artifact's recomputed digest and repeats artifact schema, complete owner repository identity, issuer, claim scope, and artifact. The verifier binds receipt roles to observation/pin IDs, node roles to bundle keys plus expected schema/owner repository/issuer/scope, and every non-artifact value to an explicit closed parameter binding. Generic authority context artifacts are forbidden. Receipt, node, and parameter role sets are pairwise disjoint and their union equals the verifier's UTF-8-sorted `required_role_ids` exactly. Observation IDs equal snapshot receipt IDs, capability IDs equal config pin IDs, and binding keys equal bundle keys. Missing, duplicate, contradictory, or surplus pins, receipts, roles, or nodes fail closed.
6. The normative rule-role manifest enumerates all 25 rules, classifies exactly 18 authority-bearing rules, and closes each static/prefix role's sources, category, owner, repository, acquisition contract/distribution/capability tuple, expected schemas, minimum/maximum cardinality, and edge IDs. Subject and authority-graph edge roles have explicit non-active mappings so no descriptor-derived role is ownership-free. `tombstone_reuse` and `projection` are authority-bearing; `publication_journal_shape` is explicitly non-authorizing. Active roles satisfy every mapping cardinality and every required role; no unmanifested role is legal. Each authority-bearing rule has edges and each non-authority rule has none. Review may challenge manifest completeness, but either validator rejects any drift from the hard-pinned full-manifest digest.
7. Universal preflight order is raw I-JSON/closed schema → subject/config/snapshot/manifest/bundle/verifier self-digest and order → exact cross-object joins and edge set → pin/receipt owner, repository, store/fact/freshness, and collator checks → exact receipt/node/parameter set closure → node key/digest/schema/repository/issuer/scope → manifest cardinality and dynamic vote/task closure. A preflight failure prevents domain evaluation. `malformed_input`, `digest_mismatch`, `issuer_scope_violation`, and `self_certification` retain section-10 precedence.
8. Domain rules consume only preflight-resolved owner receipts, proof nodes, and parameters. Canonical AK store/current records, semantic trust/revocation/publication/lifecycle heads, consumer acceptance/activation/history heads, recovery controller/runtime/epoch, vote proofs, and task observations have no subject, proof-node, generic-context, empty-value, fixture, validator, caller, or generator default. Before authority wrapping, every source case explicitly declares every required owner-read fact and complete receipt tuple: receipt kind, observation ID, role, owner repository, store ID/head/revision, action epoch, fact schema/digest/value, and decoded vote tuple. Only named missing-anchor negatives may omit exactly their declared anchor. The generator audits supplied vote facts against approvals without creating them and fails on any missing or disagreeing source. The hard-pinned `semantic-release-source-case-explicitness-audit.v13` covers all 375 source cases and records 3,225 source store tuples, 329 source vote tuples, and all 3,556 final wrapped receipts. For the ten cases that intentionally add or replace receipts, it carries a bijective registry of source→expected-final tuple mutations linked to non-empty authority-edge mutation descriptors. Python and Node independently reconstruct each expected final receipt multiset from the explicit source plus those registered mutations and compare every tuple field to the actual final snapshot; no wrapper mutation, store metadata drift, fact drift, duplicate addition, or silent mismatch is inferred away. Historical artifact integrity and action-time current authorization are separate predicates.
9. `differential-fixtures.json` is a closed `semantic-differential-fixture-manifest.v0`, not a case container. It carries protocol/revision, aggregate counts and JCS aggregate SHA-256, the complete source audit, authority manifest, exactly 139 UTF-8-sorted full authority-edge tuples, and one UTF-8-sorted unique shard inventory. Every shard row is exactly `{path,byte_length,sha256,case_count,raw_case_count}`; each path is a root-local `differential-fixtures-shard-NNN.json` basename, each byte length and raw-file SHA-256 is verified before parsing, row order equals shard index order, per-shard counts sum exactly, no listed file is missing, and no generated shard is extra. Concatenating shard `cases` and `raw_json_cases` in manifest order must reproduce aggregate counts and the manifest's JCS aggregate hash identically in Python and Node. Each authority tuple binds edge/rule/description, descriptor-derived role IDs and role-owner tuples, a closed `single_owner` or `multi_owner` aggregate, positive fixture, drift fixture, expected error, a non-empty UTF-8-sorted normalized semantic-mutation descriptor set, and a recomputed `semantic-release.authority-edge-linkage.v13` digest. The authority manifest repeats the full ownership/role/linkage object and forms an exact registry bijection. Both validators hard-pin registry, authority manifest, and source-audit digests; recompute `semantic-release.semantic-mutation-value.v13` descriptors and role ownership; and reject empty/wrapper-only mutation, shard/aggregate drift, ownership/linkage drift, or fixture labels as evidence.

## 3. Trees, capsule archive, and exact projection

1. Logical paths are relative NFC POSIX paths with no empty, `.`, `..`, backslash, NUL, drive, traversal, case-fold collision, or normalization collision. Every non-root parent directory is listed.
2. Source manifests admit regular files, directories, and bounded relative symlinks. They reject submodules, special files, hard-link ambiguity, uncommitted content, ignored additions, and source-revision drift. `clean_committed=true` is independently verified.
3. Material manifests admit only directories and regular files with significant modes `0644`, `0755`, and directory `0755`. Complete-tree verification rejects every missing, extra, duplicate, linked, sparse-ambiguous, or metadata-dependent entry.
4. `semantic-capsule-archive-linkage.v0` binds the complete archive manifest, compiled payload manifest, exact payload root, capsule metadata path, and archive format. Archive metadata is not allowed to alter payload identity.
5. `semantic-payload-projection.v0` is the complete allow-list from capsule paths to consumer paths. Each row binds path, mode, byte length, and content digest; directory rows use null length/digest. Source paths are UTF-8 sorted and unique; destination paths are independently unique. Their sets must equal, respectively, every payload entry under `payload_root` and every consumer entry. The archive entry set equals exactly the metadata path, payload root, and prefixed payload entry set; the payload root entry itself is exactly `{path: payload_root, kind: directory, mode: 0755}` and no extra archive entry is legal. `projection_mode=exact_no_extra_no_missing` is a total bijection, not merely equal row counts.
6. Capsule/archive identity is acyclic: capsule → archive linkage → archive manifest and closed metadata. The metadata contains only namespace, version, payload manifest, and fixed `no_capsule_archive_or_linkage_digest` mode; its exact JCS raw-byte digest and length equal the metadata archive entry. It cannot contain capsule, archive, or linkage digests. A materialization receipt must equal all capsule/projection/archive/manifests and the actual tree, and its coordinate must equal the coordinate constructed from the resolved capsule's namespace, semantic version, and digest. Any duplicate, omitted, extra, remapped, changed, cyclic, or drifting entry returns `projection_mismatch` before mutation. `projection` is authority-bearing: its capsule, current tombstone registry, and complete semantic-owner-issued tombstone history proof are semantic-owner nodes; its projection and material-tree nodes are exact ROCS proofs; the proof runs from the externally pinned semantic-owner genesis registry through the exact current registry with every revision, digest link, authorized delta, and cumulative entry preserved; and the external genesis digest/namespace/revision-1/lifecycle head plus the current namespace/lifecycle-head/tombstone-digest/revision agree exactly with the proof, capsule, registry, and capability-pinned receipts.
7. Source, payload, capsule archive, staged consumer tree, and active consumer tree are distinct roots. ROCS tool identity is bound by build/materialization receipts, not capsule identity.

## 4. Closed semantic-owner authority and trust

1. The semantic owner maintains immutable `semantic-owner-set.v0`, `semantic-approval-predicate.v0`, `semantic-compatibility-policy.v0`, `semantic-owner-policy.v0`, `semantic-trust-root.v0`, rotation, revocation, approval, and publication records on the owner surface.
2. The owner policy binds exact governing scope, owner set, approval predicate, compatibility policy, owner-controlled out-of-band trust bootstrap mode, prior policy, mandatory old-root rotation, and fail-closed revocation behavior. A consumer, ROCS, Pi, or AK cannot replace or mint these objects.
3. Owner-set members and key IDs are closed and unique. A vote is eligible only when its owner is active, its key is in that member's pinned key set, and its candidate digest equals the approval candidate. One owner counts once even if multiple keys vote.
4. `threshold` requires at least its exact integer of distinct eligible active owners and that integer must be in `1..active-owner-count`. `unanimous` requires exactly every active member and requires `threshold == active-owner-count`; a merely sufficient but unequal threshold is invalid. Revoked owners/keys return `trust_revoked`; absent, duplicate, or insufficient eligible owners return `approval_threshold_unsatisfied`.
5. Owner approval binds an exactly equal namespace, policy, set, and predicate chain, a closed typed action, its canonical AK decision resolved against capability-pinned AK store-head and current-record receipts for every authority-bearing approval rule (including rotation, revocation, and compatibility override), its independently recomputed `semantic-release.approval-action.v0` digest, unique votes over that same action digest, and a canonical accepted AK decision reference. Typed actions are `release`, `trust_rotation`, `trust_revocation`, `compatibility_override`, `publication_withdrawal`, or `publication_revocation`; action-specific fields are closed. Release repeats the complete coordinate plus source-manifest, candidate-capsule, and compatibility-report digests, with candidate capsule equal to coordinate capsule. Withdrawal/revocation actions repeat namespace, complete policy/set/predicate chain, coordinate, prior status/digest, operation, reason, and expected revision/head. The predicate is recomputed; the approval's existence is not itself proof that it passed.
6. The local trust chain is an independently supplied external owner-controlled root pin → owner policy/set/predicate → approval → publication → coordinate → capsule → manifests/blobs. The pin binds namespace, root ID/revision/digest, owner-policy digest, owner-set digest, and external revocation revision/head exactly; the externally observed revoked-digest set wins over a structurally valid root; publication authority resolves the root and requires every one of those facts to agree with policy/set/approval/coordinate. A capsule, consumer copy, build receipt, AK record, or Pi receipt cannot bootstrap or default the root or pin.
7. Rotation exactly binds current old-root ID/revision/digest, a closed new root whose prior digest is old root, equal namespace/policy/set/predicate across both roots, policy, rotation, and approval, new revision `old+1`, equal rotation revision, and a typed rotation approval repeating every transition and authority field. Policy, approval, root, or revision drift is `trust_reference_stale`; a revoked old root is `trust_revoked`.
8. Trust revocations are append-only records with revision `prior+1`, target kind/digest (including root), effective ledger revision, reason, and a typed approval action repeating the complete namespace/policy/set/predicate authority chain plus all transition fields, and exact prior revocation head. Locally known revocation wins over cached trust. Missing, stale, skipped, mismatched-policy, or mismatched-approval state fails closed.
9. Offline cached trust is usable only if root revision, ledger revision, and local revocation head meet the external pins. v0 does not claim protection when both the owner-controlled root store and verifier are compromised.

## 5. Executable compatibility, SemVer, and lifecycle

1. `semantic-compatibility-policy.v0` contains exactly one UTF-8-sorted rule for each of the nine closed v0 categories. Each rule fixes classification, SemVer effect, optional typed condition kind, and override permission. Policy severity is `patch < minor < major < unknown`; zero-major exceptions are absent unless explicitly enabled (v0 fixtures disable them).
2. Conditions are data, not prose. The operators are `evidence_digest_equals` (both digest operands non-null/equal), `consumer_protocol_at_least` (both integer operands non-null and actual ≥ expected), and `deprecation_interval_at_least` (same integer relation). `satisfied` equals recomputation. Condition IDs and references form a cardinality-preserving exact bijection: every policy-required condition is present once, each condition ID is referenced by exactly one change, and every report condition is referenced once; shared references, duplicate, missing, surplus/unreferenced, false, or ill-typed conditions return `compatibility_rejected`.
3. Every change is classified once under the bound policy. Overall classification/effect is the maximum. `unknown` returns `compatibility_unknown`. `identifier_reuse` is always breaking/major and never overrideable.
4. SemVer tokens match the complete anchored SemVer 2.0.0 grammar, including prerelease and build metadata. Core integers are arbitrary-length canonical digit strings and compare by digit length then lexical bytes; prerelease precedence follows SemVer and build metadata does not alter precedence; conversion to bounded machine numbers is forbidden. For prior `A.B.C` (including a prerelease), patch requires the same major/minor and a strictly greater patch integer; same-patch prerelease-only movement is rejected; minor requires a greater minor in the same major or a greater major; major requires a greater major. Regression, equality, prerelease weakening, or an insufficient bump returns `semver_violation`.
5. An override is a separately digested owner object bound to namespace, policy, the exact embedded change and independently recomputed change digest, source classification/effect, target classification/effect floor, executable true condition, and typed owner approval repeating the complete override (namespace, policy, embedded change and digest, source and target classification/effect, and full condition). The approved SemVer floor is never below the source floor; `unknown` fails closed at `major`. Override authority resolves its approval decision against capability-pinned canonical AK store and current-record receipts. Report override digests exactly equal used overrides: omission, surplus, duplicate, or drift rejects. It may resolve only policy-allowed cases; it cannot legalize identifier reuse, erase conditions, lower a SemVer floor, or bypass lifecycle.
6. Deprecation binds namespace/semantic ID/coordinate/revision and exact prior lifecycle head. Both deprecation and removal resolve `semantic-accepted-lifecycle-ledger-record.v0` plus their complete published status objects, publication authority/decision chains, transactions, prior status/journal joins, committed journals, fsynced markers, trust roots, and self-digested `semantic-publication-ledger-head.v0` canonical heads; each record equals the canonical ledger revision/head and coordinate at acceptance. Removal repeats namespace/ID, binds that deprecation digest/revision as its prior lifecycle head, requires the candidate prior lifecycle digest to equal the independently observed current lifecycle head, uses a strictly later accepted-ledger revision, binds the exact compatibility policy and equal policy interval, and binds the prior tombstone registry. The resulting registry binds the removal record as its lifecycle head. Every namespace/ID/revision/interval/head mismatch is `lifecycle_violation`.
7. The resulting tombstone registry has revision `prior+1`, points to the exact prior registry digest, carries the exact resulting lifecycle-head digest, preserves every prior entry byte-for-byte, adds exactly one removed ID with reason `removed` and the exact removal-record origin, and has no extras. Every lifecycle, reuse, and projection evaluation resolves both one self-digested `semantic-tombstone-history-proof.v0` and one independent semantic-owner `tombstone_genesis_anchor` owner-store fact carrying semantic-owner ID, namespace, genesis registry digest, constant revision 1, and genesis lifecycle head. The first proof registry must equal that anchor exactly; an internally coherent rewritten genesis is invalid. Revisions advance without gaps and bind every registry self-digest/prior-registry/lifecycle-head link. Every non-genesis delta has exactly one added ID that is absent from every earlier registry, grows cumulative entry cardinality by exactly one, and preserves all earlier entries byte-for-byte. Its `authorization_record_digest` equals both the resulting registry's current `lifecycle_head_digest` and the exact added entry `origin_record_digest`; its prior head equals the immediately preceding head; and its resulting lifecycle head is fresh relative to every prior lifecycle head, so head replay, no-op, and rollback are invalid. The proof's head tuple equals the independently read current registry and lifecycle/tombstone-head receipt. Truncation, coherent reset, dropped revision, bad link, replayed ID, non-`+1` growth, lifecycle-head no-op/rollback, standalone or coordinated wrong authorization, dropped/changed cumulative entry, reuse, or override returns `lifecycle_violation`.

## 6. Publication transaction and status machine

1. One namespace has one append-only ledger. `(namespace, semantic_version)` binds permanently to one capsule digest. Same coordinate plus same replay key is idempotent and returns the existing record; a different capsule at that version is `version_conflict` forever.
2. `semantic-publication-transaction.v0` binds operation, coordinate, operation-specific owner approval, the complete closed `approved_action` and `approved_action_digest`, expected prior revision/head, replay key, and status reason. The action digest is recomputed. `publish` has null reason and derives exactly a `release` action whose coordinate and candidate capsule come from the transaction coordinate while source/report remain transaction-bound. `withdraw`/`revoke` require a reason and derive the complete withdrawal/revocation action from transaction namespace/coordinate/reason/CAS fields, the resolved prior status/digest, and current policy/set/predicate. The approval action/digest must equal both transaction fields and that derived action; no caller-supplied expected action exists.
3. Before mutation, the publisher checks lock ownership, exact namespace, version uniqueness, current revision/head, predecessor, trust, approval, policy, source, capsule, projection/archive, and compatibility. Wrong revision is `publication_conflict`; same revision with another expected head is `publication_fork`. Neither mutates state.
4. The non-authorizing `publication_journal_shape` rule admits only `prepared/not-linearized/discard`, `committing/linearized/complete`, `committed/linearized/none`, and `aborted/not-linearized/discard`; every other tuple is `recovery_needed`. Shape acceptance grants no recovery authority. Authority-bearing `publication_recovery` separately requires a non-null complete transaction, resulting status, typed before/after state receipts, and complete prior-status/prior-journal objects. Prepared, committing, and aborted recovery require the exact non-durable intent descriptor. A committed/linearized/none replay instead requires that descriptor to be absent and the exact durable marker to be present before and after. A durable marker is forbidden before linearization and mandatory for committing completion and committed replay. Result record, revision, and head remain explicit in every journal state.
5. Identity is acyclic: transaction → resulting publication/status record → journal → marker. The resulting record binds the transaction and prior head but never journal/marker; journal binds transaction and the resulting record digest as both resulting record and ledger head; marker binds transaction, journal, the same resulting record/head/revision, and completed fsync. No raw future stub or backward digest is legal.
6. Publication stages blobs/result, fsyncs, then CASes one same-filesystem durable head as sole linearization. `semantic-publication-recovery-intent-marker.v0` is a closed recovery-controller descriptor with `non_durable_intent_only`, `fsync_complete=false`, and `durable_commit_marker_present=false`; it is never a durable commit marker. Recovery validates state effects, not only enum tuples. Journal recovery-controller ID/runtime/epoch equal capability-pinned recovery-controller receipts. `semantic-publication-recovery-state-receipt.v0` makes before state a semantic-owner proof node and after operational state a recovery-controller proof node; both bind owner/controller IDs, epoch, namespace, transaction, current recovery journal, and a closed state carrying separate intent and durable-marker digests. Before linearization, the canonical and semantic-owner before state are the prior revision/head/status; the intent is present, the durable marker is absent, and discard removes staging without changing that tuple. During committing recovery after linearization, the CAS has already happened: canonical and before state are the result revision/head/status, and completion removes staging, consumes the intent, binds the exact semantic-owner durable marker, and leaves the after tuple byte-equal to that result. A `committed/linearized/none` re-entry is a distinct idempotent branch: canonical, before, after, and result revision/head/status are byte-equal; the exact durable marker is already present in both states; intent and staging are absent; and recovery performs no CAS or other mutation. Any marker drift or state mutation is `recovery_needed`. Recovery performs no second CAS after any linearized journal. A loser never overwrites a winner; unsupported primitives perform no mutation.
7. Recovery's canonical publication revision/head/status, prior-journal digest, current recovery-journal digest, transaction digest, and expected result revision/head/status are separate semantic-owner receipts from one coherent store snapshot: complete owner repository, store ID, store head, store revision, and action epoch are identical across all nine. Every receipt value joins the exact transaction/journal/result transition. Recovery additionally resolves the complete owner approval, owner policy/set/predicate, trust root, external trust/revocation facts, and capability-pinned canonical AK store/current decision receipts. It derives the required publish/withdraw/revoke action solely from the complete transaction, prior status, reason/CAS fields, and current authority objects. The same publication-authority helper used by commit/transition requires approval action/digest = transaction action/digest = derived action/digest and recomputes threshold, trust currentness, canonical decision currentness, and vote proofs before any recovery result is accepted; a journal/state tuple alone grants no authority. Publish result repeats transaction coordinate/namespace/approval, uses revision `expected+1`, and binds expected prior head. Status results admit only `published → withdrawn`, `published → revoked`, `withdrawn → revoked`; each resolves and validates the complete prior status object, resolves the exact operation-specific authority-bound approval action, repeats operation-matching transaction coordinate/approval/reason, prior status digest, and next revision. Transaction expected prior revision/head and journal prior pointer equal capability-pinned semantic-owner publication state. The canonical prior journal’s transaction equals the prior status transaction, and its result digest/revision/head equal the complete prior status object and transaction CAS state. Lifecycle publication transactions additionally bind exact coordinate and namespace through transaction, status, accepted wrapper, and canonical ledger. Their journal/marker bind the transition digest as resulting head. Recovery resolves the exact complete resulting publication/status object, transaction, typed state receipts, the intent descriptor for an active discard/completion branch, and the full semantic-owner commit-marker object for a linearized completion or committed replay: marker transaction, journal, record, revision, and head must all equal the recovered journal; presence booleans cannot substitute for either descriptor or marker. The committed replay resolves a null intent role explicitly rather than accepting a missing context fact. Revoked is terminal; history never rewrites bytes or frees versions.

## 7. Canonical AK decision membrane and consumer chain

1. Issuer-kind checks run for every structurally valid subject before its domain rule, including expected-rejection subjects; a subject cannot hide issuer substitution behind another error. Every protocol decision uses `semantic-ak-decision-reference.v0`, never an arbitrary digest-only assertion. It binds stable AK repository/runtime, decision ID/revision/record digest, accepted ADR, scope, revocation/supersession, exact activation/evidence/rollback/stop, and a canonical AK store locator with store ID/revision/head and revocation head.
2. A usable reference is accepted, accepted-ADR, unrevoked, unsuperseded, accessible, and exact for scope. Every authority evaluation MUST receive capability-pinned AK canonical-store-head and current-decision-record receipts; no helper may default either fact from its subject. The supplied store locator must equal the independently read canonical store locator, store head, and revocation head, and the decision-record digest must equal the current record selected by that head. Copied/stale locators, stale revocation heads, or superseded records fail closed. AK links lineage; it never becomes owner authority.
3. Protocol v0 is closed to one repository and one canary: consumer identity is exactly owner `consumer-owner`, repository ID `pi-canary-consumer`, locator `local://softwareco/pi-canary-consumer`, identity revision `3`; `canary_scope` repeats that exact repository, one operator-supplied canary name, `naming_authority=operator`, cardinality `1`, `adoption_mode=single_operator_named_canary`, and `expansion_authority=new_protocol_and_decision_required`.
