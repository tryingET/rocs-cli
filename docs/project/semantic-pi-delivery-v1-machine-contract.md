# Machine-contract derivation — semantic Pi delivery v1 r22

## Authority and closure

The eleven files named by the core RFC—this file, the core RFC, the runtime/authority/validation annexes, the reviewed seccomp policy, the two reviewed Wasm files, and the three reviewed SQL files—are the complete pre-ADR normative semantic source. The problem brief, evidence note, and review plan are reviewed supporting/governance bytes but are not generator semantic inputs. Generated JSON Schema, registry, packet, validator, fixture, and embedding bytes are post-ADR implementations of these reviewed rules. They may add no field, branch, edge, domain, error class, ordering rule, or authority relation. Packet acceptance authenticates exact generated bytes but cannot choose new semantics.

Generation fails if prose does not determine one schema. The generator has no default inference escape hatch: an unclassified field, contradictory cardinality, unknown digest, or missing discriminator is `unsupported_protocol` and blocks packet generation. The reviewed `semantic-pi-delivery-v1-seccomp-policy.json` and `semantic-pi-delivery-v1-wasm-grammar.json` files are opaque normative packet-source blobs: their internal `schema` string values identify source formats but do not create protocol object-schema rows, self-digest domains, or resolver objects. Their exact file bytes are bound only by the design-source manifest, packet-file rows, and the specifically named policy/grammar blob domains. The copied Wasm algorithm is likewise an opaque packet blob. Cross-repo host fixture schema strings are acceptance-output formats and are excluded from protocol schema/domain/edge inventory. Generated objects such as seccomp compiler vectors remain ordinary registered schemas under their exact clauses.

The Unicode source compiler treats only the six validation-annex-named `UnicodeData.txt` General_Category `Cs` range-sentinel field-0 values as non-scalar source metadata. It validates their exact source/name/category/CCC/decomposition tuples and emits nothing from them. Every mapping, decomposition, exclusion, generated table entry, composition pair, and normalized output remains scalar-only. Any additional non-scalar source, any sentinel tuple drift, or any surrogate in an emitted value is `unsupported_protocol` and blocks generation.

## Closed issuer identity productions

Every field named `issuer`, `issuer_identity`, `reported_protocol_issuer`, `writer_identity`, `writer_service_identity`, `broker_service_identity`, or `finalizer_process_identity` is an exact JSON object, never a scalar or prose alias. The enclosing schema and any stated same-object discriminator select one production before digest-edge traversal. Each production has exactly the listed keys and `additionalProperties=false`:

- component protocol issuer: `{kind:"pi_extension_component",id:"pi-ontology-workflows",role:"semantic_pi_delivery_attestor"}`;
- Pi host issuer: `{kind:"pi_host",id:"@earendil-works/pi-coding-agent"}`;
- repository owner: `{kind:"repository_owner",role,repository_id}`, whose dynamic values equal the same current owner control resolution; fixed pairs are `pi-owner/pi-extensions` and `pi-host-owner/pi-mono`;
- authority owner: `{kind:"authority_owner",authority_kind,authority_role,authority_repository}`, whose values equal the same current control resolution authenticating the signature;
- launch broker: `{kind:"pi_host_launch_broker",owner_role:"pi-host-owner",repository_id:"pi-mono",component_id:"pi-coding-agent-launch-broker"}`;
- durable sink: `{kind:"pi_host_durable_sink",id:"pi-host-durable-artifact-store-v1"}`;
- replay writer: `{kind:"production_replay_writer",owner_role:"pi-host-attestation-owner",owner_repository,store_id}`, joined to the selected replay channel, acquisition pin, and control resolution;
- host-attestation root: `{kind:"host_attestation_trust_root",owner_role,owner_repository,root_id,root_revision,verification_key_id}`, joined to the statement-selected trust root, with statement `signing_key_id=verification_key_id`;
- fixed controller and finalizer authority identities: the exact `controller_identity` and `finalizer_identity` value objects defined by the core RFC;
- broker-attested finalizer process: `{role:"finalizer",launch_id,pid,starttime,proc_directory_inode,host_executable_launch_receipt_digest}`, used by every field literally named `finalizer_process_identity` and joined to the current finalizer launch receipt;
- production recovery actor: `{kind:"appointed_production_recovery_actor",owner_role,owner_repository,production_owner_appointment_digest,authority_control_artifact_digest,recovery_actor_launch_receipt_digest}`;
- integration recovery actor: `{role:"integration_recovery_actor",launch_id,pid,starttime,proc_directory_inode,host_executable_launch_receipt_digest}`.

Assignment is exhaustive. Delivered receipts, integration acknowledgements, and `pi.wasm-component-claim-projection.v1` use the component issuer. Suppressed/failed receipt branches, application witnesses, redemptions, replay probes, and second-attempt suppressions use the Pi-host issuer. Component/host provenance, owner approvals, and `pi.durable-artifact-store-genesis-receipt.v1` use the corresponding repository owner; the genesis receipt is fixed to `pi-host-owner/pi-mono`. `pi.host-executable-launch-receipt.v1`, closure-probe observations, integration recovery requests, recovery-writer resolutions, broker reap observations, and broker pidfd transfers use the launch broker. `pi.production-recovery-actor-launch-receipt.v1` uses the authority-owner production with `authority_kind="production_recovery_owner"` and role/repository equal to its current recovery-owner appointment. Durable acknowledgements use the durable sink. Controller-transcript acknowledgements, ordinary integration terminal observations, reservation requests, operational failure evidence, integration proofs, and `pi.host-lineage-closeout.v1` use the fixed finalizer authority identity; the closeout uses only a current host-owner key whose purposes contain `host_lineage_closeout` and whose control/pin/read closure is embedded in that object. Reservation acknowledgements, replay channel pins/read receipts, replay exchange resolutions, and replay append receipts use the replay writer. Production recovery queries, transfer requests/acknowledgements, teardown, abandonment, and failure evidence use the production recovery actor. Host-attestation statements use the host-attestation-root production. Owner cancellation evidence uses the authority-owner production selected by `authority_role`. `semantic-release.pi-integration-cancellation.v1` uses that same evidence-selected authority-owner production for `owner_cancelled`; `decision_revoked|packet_acceptance_revoked|authorization_expired` use the fixed finalizer authority identity under current host-owner `integration_cancellation` signing authority. Recovery-issued integration terminal observations use the integration-recovery-actor production. Any schema not named here that contains one of these identity fields must explicitly select one of these productions in its own clause or generation fails. Unknown production is `malformed_input`; a structurally valid but wrong fixed or dynamically joined identity is `issuer_scope_violation`. These inlined values introduce no separate artifact, schema, domain, or resolver body.

## Schema compiler

For every object introduced with “is exactly” or “exact keys”:

1. Emit one draft-2020-12 object schema with `type=object`, `required` equal to the listed keys, and `additionalProperties=false`.
2. A key ending `_digest` is a canonical `sha256:` string unless its exact clause says null or another lexical value; `_digest_or_null` is the union with null.
3. A key ending `_utc` uses the exact 30-byte UTC pattern; `_nonce` uses 64 lowercase hexadecimal; `_kind`, `_role`, `_mode`, `_state`, `_outcome`, `_reason`, `_scope`, and `_status` use only their clause's closed literals. Dynamic identifiers use the clause's canonical NFC pattern; numeric AK task/evidence IDs are canonical unsigned decimal strings.
4. Byte lengths, ordinals, revisions, sequences, epochs, PIDs, inodes, offsets, and monotonic values are safe nonnegative JSON integers. Boolean fields are JSON booleans only.
5. “Sorted/unique rows” emits an array whose item schema is the exact row object and whose semantic validator enforces the stated order and uniqueness. “Exactly empty” emits `minItems=0,maxItems=0`; exact cardinality emits equal `minItems`/`maxItems`; every other array emits `minItems=0,maxItems=100000` unless a reviewed narrower bound is stated.
6. A clause saying a field is null/non-null by branch emits a `oneOf` branch selected by the stated discriminator. No implicit optional fields exist.
7. Exact nested objects are inlined only when the clause calls them values or rows; every named artifact is a digest edge and its body appears only in the resolver artifact set.
8. String input first passes strict UTF-8 and reviewed Unicode-15 NFC; JSON numbers follow the integer-only profile. Schema acceptance never weakens semantic validation.

Canonical schema emission uses no synonym choices. Every schema root has exactly `$schema,$id,type,properties,required,additionalProperties` and, only when branch rules exist, `oneOf`; `$schema` is `https://json-schema.org/draft/2020-12/schema`, `type` is `object`, `required` preserves the exact field order in the reviewed object clause, `properties` contains every field once, and `additionalProperties=false`. No `$defs`, `format`, `title`, `description`, `default`, `examples`, redundant keyword, singleton `enum`, or boolean schema is legal. An unconstrained semantic string uses `{type:"string"}`; a patterned string uses exactly `{type:"string",pattern:P}`; a literal uses `{const:value}`; a closed multi-literal set uses `{enum:[values]}` in unsigned-UTF-8 lexical order; a boolean uses `{type:"boolean"}`; a safe integer uses `{type:"integer",minimum:0,maximum:9007199254740991}` plus reviewed narrower bounds; a null uses `{type:"null"}`; a nullable value uses `oneOf` with null first and the non-null schema second; an array uses `{type:"array",items:...,minItems:...,maxItems:...}` and `uniqueItems` only when exact JSON-value uniqueness is normative. Exact nested values recursively use the same object production; artifact bodies use an absolute `$ref` only when the reviewed clause calls for an embedded value rather than a digest. Branch `oneOf` entries sort by the discriminator literal's unsigned UTF-8 bytes and each branch contains exactly `properties` with the discriminator `const` plus the branch-specific nullability schemas and `required` for those keys.

Fixed string patterns are literal JSON strings: digest `^sha256:[0-9a-f]{64}$`; 64-hex nonce `^[0-9a-f]{64}$`; 40-hex commit `^[0-9a-f]{40}$`; unprefixed SHA-256 `^[0-9a-f]{64}$`; canonical decimal ID `^(0|[1-9][0-9]*)$`; UTC `^[0-9]{4}-(0[1-9]|1[0-2])-([0-2][0-9]|3[01])T([01][0-9]|2[0-3]):[0-5][0-9]:[0-5][0-9]\\.[0-9]{9}Z$`; logical ID `^[a-z][a-z0-9._/-]*$`; and permissions `^[r-][w-][x-][ps]$`. Calendar validity, NFC, UTF-8 byte length, semantic ordering, and cross-field bounds remain semantic-validator checks, never alternate schema encodings.

Schema names equal each object's literal `schema` value. Each schema file path is exactly `schemas/` plus the schema name plus `.schema.json`; its `$id` is `https://ai-society.local/rocs/semantic-pi-delivery-v1/` plus that path, every internal reference is an absolute `$id`, and the file is RFC 8785 JCS UTF-8 with no BOM or trailing LF. As the sole root exception, `protocol.schema.json` is exactly `{$schema:"https://json-schema.org/draft/2020-12/schema",$id:"https://ai-society.local/rocs/semantic-pi-delivery-v1/protocol.schema.json",oneOf:[{$ref:absolute_schema_id},...]}` with refs in UTF-8 schema-name order, JCS UTF-8, no BOM/trailing LF, and no other key or free-form fallback. Python and Node independently compile these paths and bytes from the reviewed objects without shared generator code; byte or inventory disagreement blocks packet generation.

Every exact object clause must classify every listed field by literal, lexical profile, scalar type, exact nested row/value, digest edge, or explicit branch matrix. Suffix rules are consistency checks, never authority to invent a missing type. `details` wherever present is an unsigned-UTF-8 `(key,value)`-sorted unique array of exact `{key,value}` rows; both are NFC strings of 1..256 UTF-8 bytes. `related_artifact_digest` in a delivery error is removed: a delivery error has no generic artifact pointer because its target cannot be selected before resolution.

## Digest-edge compiler

Every digest-shaped field receives exactly one registry row.

1. The object's own registered self-digest field is `non_edge`.
2. Derived execution-instance, prompt-attempt, aggregate, head-lineage, and statement digests explicitly called preimages are `non_edge`.
3. Exact-byte fields map to the named domain in the complete digest registry.
4. A field whose name is another schema's self-digest field maps to that schema.
5. `subject_digest` is discriminated by `subject_kind`; `artifact_digest` by `artifact_kind`; cancellation/terminal evidence by reason; nullable branches preserve the same target with nullable cardinality.
6. Row `content_digest` is discriminated by its enclosing row role/domain. Packet rows always target `semantic-release.pi-packet-file-bytes.v1`.
7. Registry `schema_digest` is a reviewed derived `non_edge`, not a second blob edge. Its bytes are reached only through `packet_bindings.file_path` and the packet row's `semantic-release.pi-packet-file-bytes.v1` blob; validators recompute `semantic-release.pi-schema-file-bytes.v1` over those same bytes and compare. A second schema-domain blob row is forbidden. SQL bindings use the same single-blob rule: every `schema_sql_digest` is a derived `non_edge`, exact `sql_bindings.file_path` supplies the sole packet-file blob, validators recompute the row's specialized SQL domain over those same bytes, and a second SQL-domain blob is forbidden. The three source/path/domain pairs are fixed by the validation annex and their source files are reviewed bytes. Design-source and v0-baseline manifests are the only reviewed dual projections. Each external `design_source_manifest_digest` or `v0_baseline_manifest_digest` remains an ordinary object edge to its named schema/domain and resolves one object row. The corresponding fixed packet path independently resolves one packet-file blob row under `semantic-release.pi-packet-file-bytes.v1`. Exact JCS bytes of the object row must equal decoded blob bytes byte-for-byte, and object self-digest, packet content digest, ordinary file SHA, and packet-manifest row all recompute. Projection cardinality is entrypoint-dependent: a resolver artifact set that reaches either manifest through an object edge contains both object and blob rows; packet and `module_closure` contain only the packet blob unless another reviewed root actually reaches the object digest. When an object edge is reached, missing either projection rejects; when none is reached, an unrooted object row rejects as unreachable. A third copy or byte drift always rejects. Packet-manifest bootstrap keeps its separate single-blob exception.
8. A field with more than one possible target must have a source-side discriminator in the same object. Resolving a target first to discover its schema is forbidden. `durable_store_initial_anchor_kind=genesis_receipt|recovered_read_receipt` selects respectively `pi.durable-artifact-store-genesis-receipt.v1` or `semantic-release.authority-store-read-receipt.v1`.
9. Authority artifacts are branch-classified before traversal. In a `v0_authority_proof` control resolution, `accepted_authority_artifact_digest`, `semantic_owner_artifact_digest`, and `trust_basis_digest` are reviewed `non_edge` values validated inside the v0 proof bundle. In appointment-backed control, `accepted_authority_artifact_digest` and every `appointed_owner_control_artifact_digest|authority_control_artifact_digest` target `semantic-release.pi-authority-control-artifact.v1`, while `trust_basis_digest` targets the discriminator-selected host-attestation or production-owner appointment. No target may supply the keys that authenticate itself.
10. A field with more than one possible target and no reviewed discriminator blocks generation. Unknown and duplicate edges block generation.

The generated registry must round-trip this compiler: sorting its schema/domain/edge rows and regenerating schemas yields byte-identical inventories on Python and Node implementations.

## Seccomp policy compiler

`pi.reviewed-seccomp-policy-compiler.v1` accepts only the reviewed x86-64 policy JSON, including numeric constants, ordered denials, and the syscall-number-sorted unique allowlist; ambient headers and kernel syscall tables are forbidden inputs. It emits classic BPF from this exact symbolic program: `LD_W_ABS arch; JEQ architecture +1 else +0; RET KILL_PROCESS; LD_W_ABS nr; JSET x32_syscall_bit +0 else +1; RET KILL_PROCESS;` then each denial in JSON order, each allow row in JSON order, and final `RET KILL_PROCESS`. An unconditional denial emits `JEQ syscall +0 else +1; RET ERRNO|errno`. A masked denial emits `JEQ syscall +0 else +3; LD_W_ABS args_offset + 8*argument_index; JSET mask +0 else +1; RET ERRNO|errno`. An allow row emits `JEQ syscall +0 else +1; RET ALLOW`. All jumps are forward relative instruction counts and must fit unsigned eight bits. Instruction codes are exactly `LD_W_ABS=0x20`, `JEQ_K=0x15`, `JSET_K=0x45`, and `RET_K=0x06`. Each `sock_filter` is serialized as little-endian `u16 code || u8 jt || u8 jf || u32 k`; concatenation has no header or padding. On x86-64, each tested mask is in the low 32-bit syscall argument word at `args_offset + 8*argument_index`. Unknown architecture, every x32 number, and every unlisted native syscall kill in kernel before dispatch. Listed executable-memory syscalls reach `ALLOW` only when their denial predicate is false; unconditional denials never appear in the allowlist. A matched denial returns `SECCOMP_RET_ERRNO|EPERM`; no ambient or future syscall receives implicit allow.

Installation is exactly `PR_SET_NO_NEW_PRIVS=1` then `seccomp(SECCOMP_SET_MODE_FILTER,SECCOMP_FILTER_FLAG_TSYNC,program)`, followed by `PR_GET_NO_NEW_PRIVS=1` and `PR_GET_SECCOMP=2`. Before extension bytes are read, one sacrificial `clone3(CLONE_PIDFD)` child immediately closes every inherited protocol, capability, source-bundle, ledger, and durable-channel descriptor, verifies only stdin/stdout/stderr remain, then maps one private RW page, attempts exactly `mprotect(page,4096,PROT_READ|PROT_EXEC)`, requires `-1/EPERM`, unmaps, and exits zero; the parent requires the pidfd to report that exact clean exit and records `pi.seccomp-self-test-observation.v1` exactly `{schema,seccomp_policy_digest,seccomp_bpf_digest,test_syscall,test_arguments,observed_return,observed_errno,child_exit_status,seccomp_self_test_observation_digest}`. Test syscall is `mprotect`, arguments are exact `{length:4096,protection:5}`, return is `-1` represented by literal string `minus_one`, errno is `EPERM`, and status is `0`. This is the sole expected denied call and occurs in the sacrificial child; every later denied call in a witness-capable process aborts. The broker-attested standalone host executable contains the reviewed fail-stop wrapper: after self-test, any listed denial returning `-1/EPERM` causes immediate `_exit(159)` before another protocol write, witness operation, or extension instruction. Broker map/executable verification binds this wrapper to the exact host bytes; an option string or caller convention cannot substitute. Kernel default-kill closes unknown-syscall evolution, while the wrapper closes the intentional EPERM branches. Compiler bytes/digest are joined by the host manifest and both runtime observations; the run-specific self-test observation is joined by both runtime observations and the execution transcript. Packet known-output vectors cover unknown architecture, x32 number, allowed native call, denied native calls including `mremap`, and exact instruction bytes; the host-owner runtime fixture separately covers the self-test result.

## Error and vector compiler

The precedence taxonomy and every mandatory vector ID/entrypoint/expected result are fixed by the validation annex; fixtures may instantiate but never define those semantics. Literal synthetic keys, timestamps, nonces, seed bytes, and byte mutations are post-ADR implementation evidence, deliberately not pre-ADR semantic source. Their selection is lawful only through the generated derivation/coverage artifacts below; it cannot change an ID, route, expected class/relation, protocol field, or rule.

`semantic-release.pi-vector-derivation-manifest.v1` is exactly `{schema,profile,seeds,cases,vector_derivation_manifest_digest}`. Profile is `r22-mandatory-and-boundary`; seeds are ID-sorted exact `{seed_id,entrypoint,clock,request,blobs,seed_sha256}` rows using complete fixture-case input shapes; `seed_sha256` is ordinary lowercase unprefixed SHA-256 over RFC-8785 JCS bytes of exact object `{entrypoint,clock,request,blobs}` with those four keys and the same nested case shapes/order rules; it excludes `seed_id` and `seed_sha256` and has no BOM/trailing LF. cases are mandatory-ID-sorted exact `{id,rule_ids,mutation_intent,seed_id,entrypoint,steps,expected}`. Rejected-case `rule_ids`, mutation intent, entrypoint, and expected error/relation copy the pre-ADR case-intent row byte-for-byte; ordinary rejected cases have exactly one rule ID and precedence cases exactly two in reviewed order. Accepted cases instead copy ID/entrypoint/relation from the validation annex's exact accepted-case table, use exactly empty rule IDs, mutation intent `accepted_seed`, and empty steps; no accepted case-intent row is required. Each step is exactly one discriminator branch: `{kind:"json_replace",target,pointer,expected_old_jcs_base64,replacement_jcs_base64}`, `{kind:"json_remove",target,pointer,expected_old_jcs_base64}`, `{kind:"json_insert",target,pointer,expected_absent,replacement_jcs_base64}`, or `{kind:"byte_splice",target,offset,expected_old_base64,replacement_base64}`. Target is `clock|request|blob/<logical_id>`; pointers are canonical RFC6901; JSON byte values are exact JCS; base64 is canonical padded standard except key/signature fields whose object values retain their own encoding. Steps apply in listed order and every changed digest/signature/length/enclosing object is an explicit later step—no implicit reclose. Seed SHA-256, expected old bytes/value/absence, final case bytes, route, and result all revalidate. Accepted cases have empty steps. Missing/extra case, seed drift, unlisted step kind, name-derived mutation, or route/result disagreement blocks fixture acceptance.

`semantic-release.pi-rule-coverage.v1` is exactly `{schema,profile,rules,rule_coverage_digest}` with profile `r22-frozen-rejection-obligations`; rules are sorted/unique by `(coverage_kind,coverage_id,rule_id)` and each is exactly `{rule_id,coverage_kind,coverage_id,validation_surface,entrypoint,error_code}`. The inventory is closed entirely by reviewed bytes; no source-anchor choice, branch discriminator, implementation label, hash-derived rule ID, or post-ADR row invention exists. `coverage_kind` is `mandatory_case|boundary_case|host_fixture`. For every rejected non-boundary case in the reviewed case-intent map, emit one `mandatory_case` row for each listed rule ID: `rule_id` is that exact `case.*` value, `coverage_id` is the exact case ID, surface is `python_and_node`, entrypoint/error copy the same reviewed row, and precedence cases therefore emit exactly two rows. The three IDs `activation-not-current|deadline-equality|resource-json-file-limit` are excluded from mandatory emission; accepted mandatory cases emit no rejection row. This produces exactly 99 mandatory rows after canonical tuple sorting. Emit exactly three `boundary_case` rows with rule IDs `boundary.activation-not-current|boundary.deadline-equality|boundary.resource-json-file-limit`, matching same-named coverage IDs, surface `python_and_node`, and the entrypoint/error pairs frozen in the validation annex. Emit exactly one `host_fixture` row for each of the twenty-five exact Pi-host fixture IDs frozen in the validation annex, with rule ID `host.` plus that fixture ID, matching coverage ID, surface `pi_host`, and null entrypoint/error because their reviewed outcome is a host/finalizer fail-closed boundary rather than a ROCS entrypoint error. The complete sorted inventory has exactly 99 mandatory rows, 3 boundary rows, and 25 host rows, 127 total. No other row is legal. Both independent validators derive the mandatory and boundary inventory directly from the reviewed map/annex and compare exact rows; the Pi-host owner gate compares the host inventory before executing it. Coverage is intentionally grouped obligation coverage, not an implementation-branch bijection: an owner may split or merge internal rejection branches only if every frozen obligation still executes with its exact reviewed outcome and introduces no schema or protocol semantics. This artifact records traceability, not new semantics; any desired obligation, ID, route, or outcome change requires an RFC revision.

The first post-ADR ROCS implementation authors these artifacts and canonical fixture bytes, then Python and Node independently replay every derivation step, verify the exact frozen coverage inventory/outcomes, and execute the same cases without shared fixture builder or validator code. Once packet acceptance authenticates their exact hashes, write/check reruns must be byte-identical. Their absence before ADR is expected and cannot be treated as implemented behavior; their absence or disagreement after ADR blocks packet acceptance, implementation readiness, and dogfood. Host-owner fixtures follow the same no-new-expectation rule under their owning implementation task.

## Reviewed-source check

`semantic-release.pi-design-source-manifest.v1` is exactly `{schema,rfc_revision,reviewed_commit,review_aggregate_sha256,files,design_source_manifest_digest}`. Revision is `semantic-pi-delivery-v1-r22`; commit is 40 lowercase hexadecimal; aggregate is 64 lowercase unprefixed hexadecimal. Files are unsigned-UTF-8 path-sorted unique `{path,source_role,byte_length,sha256}` rows covering exactly the review-set plan; `source_role` is `normative_semantic_source` for the eleven core/annex/machine-source files and `reviewed_supporting` for the problem brief, evidence note, and review plan. Aggregate computation still uses the review plan's ordinary `path<TAB>byte_length<TAB>sha256<LF>` rows and does not include `source_role`. `design_source_manifest_digest` uses domain `semantic-release.pi-design-source-manifest.v1` and omits itself. `scripts/generate-semantic-pi-delivery-v1.py --check-packet` recomputes it; packet acceptance repeats its digest, commit, and aggregate. Any source-byte drift requires a new RFC review; regeneration alone cannot bless it.
